Your own Farcaster client.
Your own node. Three commands.

No API keys from anyone. You furnish the compute; a Snapchain read node syncs the network; the Fiddy client reads and writes through it. Then — the part no other client has — hatch your own Hermes agent that works for you 24/7.

0 fiddy provision --gcpfurnish the compute — or the one-click Cloud Shell button below; --ssh you@server for any box you have
1 fiddy node upinstall + sync a Snapchain read node on it
2 fiddy client upboot the Fiddy client pointed at your node

Get the CLI: git clone https://github.com/ivcained/fiddy && cd fiddy — the bin/fiddy script is the whole tool. Full tutorial below.

Before you type anything

How Farcaster actually fits together

Farcaster is hybrid: identity lives onchain (OP Mainnet), data lives offchain. Onchain is used only when security and consistency are critical — creating an account, paying storage rent, registering keys. Everything social — casts, follows, reactions, profile pictures — is an offchain message signed by a key the chain knows about.

PieceWhat it is
FIDYour account number, minted onchain to your custody address. Everything you do offchain references it.
Custody addressThe Ethereum key that owns your FID. The master key. It authorizes everything else and touches nothing day-to-day.
App key (signer)An ed25519 key a client uses to sign messages for your FID. Authorized by your custody address. Revocable. This is what "log in to a client" means under the hood.
SnapchainThe peer-to-peer network storing all user data. Validators propose blocks; read nodes follow, store, and serve APIs.
Storage rentA small onchain payment that buys your FID the right to store data. No rent, no writes. (Your account already has storage if you've used Farcaster.)
Command 0

0fiddy provision

A read node needs a server: 4 vCPU, 16 GB RAM, 1.5–2 TB free disk, Ubuntu 22.04+. The mainnet snapshot is ~200 GB compressed and takes several times that once decompressed — size for 1.5–2 TB, not 200 GB.

Cheapest → costliest: Hetzner ~€120 · OVH ~$190 · AWS ~$285 · GCP ~$350

Google Cloud, one click. Cloud Shell opens pre-authenticated with a guided walkthrough: one command creates the VM, disk and firewall, in your project, on your billing. This exact path ran our own verified node (914M messages synced). Hetzner is the cheapest (~€120/mo, fiddy provision --hetzner) but that path is not yet battle-tested — the ladder is in the miniapp: fiddy.fun/client/deploy.

~$350/mo (e2-standard-4 + 2 TB disk — our own GCP bill). New to GCP? You get $300 in free credit — the node is free to start. Set a calendar reminder to delete the VM (or downgrade) before the credit runs out so nothing surprises you. Prefer a guided page? fiddy.fun/client/deploy. Prefer the terminal? fiddy provision --gcp (needs the gcloud CLI signed in).

Other providers — same three commands, your pick 
# AWS (needs the aws CLI configured, ~$285/mo list):
fiddy provision --aws

# Hetzner (CCX33 + 2 TB volume, ~€120/mo — token from console.hetzner.cloud):
fiddy provision --hetzner

# OVHcloud Public Cloud (b3-16 + 2 TB volume, ~$190/mo — creds from api.ovh.com/createToken):
fiddy provision --ovh

# Or any server you already have:
fiddy provision --ssh ubuntu@203.0.113.10

Hetzner and OVH paths are scripted against their API docs but not yet battle-tested — they fail loudly with the provider's own error if anything drifts. A 2 TB box at any Hetzner / Contabo / OVH-class host typically runs $50–120/month. Infra-as-code people: the same validated GCP config ships as a Terraform module in terraform/gcp-read-node/ (terraform apply, prints the next commands).

Every scripted path creates a 4 vCPU / 16 GB machine with a ~2 TB disk and Docker preinstalled, then saves the target to ~/.fiddy/config. The AWS path also generates an SSH keypair into ~/.fiddy/ and locks the security group down: SSH and the node API answer your IP only; gossip ports stay open to the network (that's how your node talks to peers).

Command 1

1fiddy node up

This installs Docker and the official Snapchain bootstrap on your server and starts syncing. You now run a read node: it follows the chain, stores the full state, and serves the HTTP (:3381) and gRPC (:3383) APIs. Anyone can run one. No permission, no API keys.

fiddy node up      # install, start, wait for the API to answer
fiddy node status  # sync progress
fiddy node logs    # tail the node
fiddy node dashboard # Grafana (sync height, peers, shards) via SSH tunnel → localhost:3000
fiddy node autoupgrade on # weekly upgrades (Tue 03:00). Default off: the upstream job ends with a host-wide docker prune — fine on a dedicated box, never on a shared one
Read nodes vs validators — and where your casts go

Validators propose and vote on blocks; only keys in the validator set can. Read nodes do everything else — including accepting writes.

When you submitMessage to your read node, it validates the message and gossips it to validators — a read node has no mempool of its own. A success response means "valid, accepted for relay," not "in a block." Confirm inclusion by watching for a MERGE_MESSAGE event or querying the message back. Under heavy network load a gossiped message can drop and need resubmitting; the client can fall back to submitting at a validator endpoint, and this tutorial shows you the trade-off when it matters.

Full sync takes hours; the API answers immediately and catches up in the background.

Command 2

2fiddy client up

Boots the Fiddy web client pointed at your node for reads and writes. If your node's API is locked to your IP (the AWS default), add --tunnel and the CLI opens an SSH tunnel for the session.

fiddy client up --tunnel

Signing in = giving the client its own key. Import the seed phrase of an account that already has storage. The client derives your custody address, and uses it once — to sign a gasless KEY_ADD message that registers a fresh ed25519 app key for the client. No Optimism transaction, no ETH, confirmed in seconds. From then on the custody key sits idle and the app key signs your casts, follows, and reactions — scoped, capped, and revocable from the UI with a KEY_REMOVE.

Seed phrases: powerful, handle like rm -rf

A seed phrase is your custody address is your FID. Anyone holding it owns the account. Follow this tutorial with a test account only. In general, paste a seed phrase only into software from developers you trust, running locally, source available — this repo is MIT and the phrase never leaves your browser, but verify that yourself; that's the point of open source. Wherever possible prefer delegated signer authorization (approve an app key from an already-authenticated client) over seed import.

From here the client is fully yours: read the feed from your node, post casts, follow, react, and include or exclude casts from any other client in your view settings.

The part no other client has

Hatch your Fiddy agent

One click in the client provisions a dedicated Hermes instance on Agent37 cloud — not a chatbot, a real agent with its own computer, awake 24/7. It lives in your client, chats with you there, and runs scheduled jobs: "check my mentions every morning," "draft my weekly recap cast."

Through Hermes, your Fiddy reaches every channel you do — with your explicit approval on each one:

FarcasteriMessageDiscord TelegramWhatsAppEmailWeb & API

Your agent acts on Farcaster under its own FID and its own gasless app key — clearly the agent's voice, revocable by you at any time. It reads from the same node you just stood up: the whole stack, end to end, nobody's API key in sight.

Questions you'll hit

QuestionAnswer
Does this cost ETH?No. App keys are gasless KEY_ADD messages since Snapchain V16. You need an existing account with storage rent paid — that's all.
Can my node accept casts?Yes — read nodes validate and gossip writes to validators. They hold no mempool, so under load a write can drop; watch for MERGE_MESSAGE or query it back, and resubmit if needed.
What can the app key do?Only the message types you scope it to (casts, reactions, links, user data). Keys slide-expire in at most 90 days, cap at 1000 per FID, and revoke instantly with KEY_REMOVE.
Where's the custody key?In your browser, used once for the EIP-712 KEY_ADD authorization, then idle. Never sent anywhere, never stored server-side.
Who am I depending on?Your compute provider for uptime, and the Snapchain validator set for block production — the same set every client depends on. Reads, writes, and identity tooling are all yours.
